# Failure test: ctl1

Started 2026-10-19 17:03. Power cut with `echo o > /proc/sysrq-trigger` (no sync, no clean shutdown); power restored with Hyper-V `Start-VM`.

## Findings

- East-west (web -> build, same network): ping seq: 513 samples, longest gap 1 (a gap of 1 means no loss).
- Routed traffic (web -> 1.1.1.1 via the router on ctl1): ping seq: 28 samples, longest gap 478 seconds.
- Disk writes inside web (Ceph-backed volume): io writes: 479 samples, longest gap 27 seconds.

## Operator notes

- **Power-on delay:** the first UAC prompt at t+124 was not approved; ctl1 actually started at 17:08:49 after a second prompt. Measure recovery from "ctl1 back on the network" (t+328): Keystone +144 s, all Nova services +179 s, Neutron agents +181 s, routed traffic back about +150 to +180 s.
- **Data plane vs control plane:** with the controller off, VMs kept running and talking to each other across hosts (VXLAN between computes needs no controller). Only traffic through the department router stopped, because the L3 agent runs on ctl1.
- **27 s disk stall:** writes inside `web` paused while Ceph still counted ctl1's OSD as up (heartbeat grace before marking it down). PGs whose primary OSD was on ctl1 blocked until then, then continued on the remaining two copies.
- **Stale security-group members after recovery:** the isolation test afterwards failed 2 of 40 checks: `build` (cmp1) could not reach `web` (cmp2) in the same department. On cmp2 the ipset behind web's "same security group" rule held only web's own IP; build's was missing. Restarting `neutron_openvswitch_agent` on cmp2 rebuilt the set and all 40 checks passed. A plain live migration did not reproduce it, so the likely cause is member updates lost while RabbitMQ (on ctl1) was down. Recovery now ends with the isolation test (see the controller runbook).
- **MariaDB:** the single-node Galera cluster came back by itself after the hard power cut in both runs; `kolla-ansible mariadb_recovery` was not needed.
